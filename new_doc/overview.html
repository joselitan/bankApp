System Overview

Architecture, technology stack, and key design decisions behind the SecureCore Bank MVP backend.

What the System Does

SecureCore Bank exposes a REST API that enables a client (e.g. Postman, a mobile app, or a web frontend) to:

  • Register a new user and receive a default Savings account automatically
  • Log in with email + password and receive a short-lived JWT Bearer token
  • View their account balance and the last 10 transactions
  • Deposit money into their account (between $1.00 and $10,000.00 per operation)
  • Transfer money to another registered user (min $0.01, $5,000 daily outgoing cap)
  • Log out (stateless — the client discards the token)

Every meaningful action is stored in an audit log table for traceability. All money-moving operations are wrapped in a single database transaction to guarantee atomicity.

Architecture Layers

The application follows a clean, layered architecture where each layer has a single responsibility.

LayerLocationResponsibility
HTTP Client External (Postman, curl, web app) Sends HTTP requests; receives JSON responses
FastAPI Routes app/api/v1/ Receives requests, validates input via Pydantic schemas, returns responses. Handles HTTP-level concerns (status codes, auth headers).
Dependency Injection app/api/deps.py Provides the authenticated User object and DB session to route handlers via FastAPI Depends().
Services / Business Logic app/services/ Encapsulates domain rules: password policy, lockout logic, account number generation, and audit log writing. Framework-independent.
ORM Models app/models/ SQLAlchemy 2.x mapped classes representing database tables (User, Account, Transaction, AuditLog).
Pydantic Schemas app/schemas/ Request / response data shapes. Separate from ORM models, preventing accidental data leakage.
Database securecore_bank.db SQLite file. Managed via SQLAlchemy; swappable to PostgreSQL by changing DATABASE_URL.

Security Design

ConcernImplementation
Password storage PBKDF2-SHA256 via passlib. Passwords are never stored in plain text. The hash is one-way.
Password policy Min 8 characters, at least 1 digit, at least 1 special character (enforced server-side via regex).
Authentication JWT Bearer tokens (HS256). Tokens expire after 30 minutes. The sub claim holds the numeric user.id.
Brute-force defense Account locked for 10 minutes after 3 consecutive failed login attempts. Lock state stored in the users table.
Error leakage Login returns a generic "Invalid credentials" message whether email or password is wrong, preventing user enumeration.
Transaction atomicity Transfer operations flush all DB writes in a single db.commit(). Any exception triggers db.rollback().
Audit logging Every meaningful action is written to audit_logs including IP address, user_id, amount, and detail string.

Key Design Decisions

SQLite for MVP

SQLite was chosen for zero-config local development. The ORM abstraction layer (SQLAlchemy) means switching to PostgreSQL in production requires only a change to the DATABASE_URL environment variable.

One account per user

The MVP assumes exactly one Savings account per user. The data model supports multiple accounts (via the user_id FK on accounts), but all business logic currently queries for the first account found.

Stateless JWT logout

The POST /auth/logout endpoint is intentionally a no-op on the server — it returns {"logged_out": true}. Token revocation is not implemented in the MVP. The client is responsible for discarding the token. A short expiry (30 minutes) limits the exposure window.

Naive UTC timestamps for SQLite

SQLite has limited timezone support. Lockout timestamps use naive UTC (datetime.utcnow()) for correct comparison. Created-at timestamps use timezone-aware UTC via datetime.now(UTC).

Service layer is framework-agnostic

The app/services/ functions only accept SQLAlchemy Session objects and domain models — no FastAPI Request or Response types (except optionally the Request for IP extraction in audit logging). This keeps business logic easily testable and portable.
