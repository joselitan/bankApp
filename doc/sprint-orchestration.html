What this page adds

A practical operating system for running “agent sprints”

The overview page lists useful agent types. This page shows how to run them like a team: planning from Jira, executing work as PRs, validating via CI, transitioning Jira tickets, closing the sprint, and selecting the next sprint.

Source of truth Jira backlog Execution PRs in your repo Truth detector CI + tests
Quick checklist
Small PRs: 1 story per PR (or smaller).
Green CI: no “Done” without passing tests.
Human gates: approve sprint plan + merge PRs (initially).

1) The core operating model

Inputs agents read

  • Jira issues (Epics/Stories): descriptions, acceptance criteria, priority, dependencies
  • Sprint context: capacity, sprint goal, definition of done (DoD), constraints
  • Repo state: architecture, current tests, CI results, existing docs

Outputs agents produce

  • PRs with code + tests + minimal docs
  • Jira updates: comments, status transitions, links to PR/CI
  • Sprint report: shipped items, known issues, carryover, risks
Key rule: Jira is the work queue, but the repo + CI are the truth. Agents should optimize for small increments that keep CI green.

2) The agent team (roles you can scale)

Avoid a single “mega agent”. Use small specialists with clear responsibilities. Your orchestrator coordinates. Worker agents build and validate.

Sprint Orchestrator Agent Coordinator

  • Select sprint scope from Jira based on priority + dependencies
  • Create a sprint plan and assign stories to worker agents
  • Track progress, handle retries, escalate blockers
Output: SPRINT_PLAN.md + work queue + status updates

Backlog Groomer Agent

  • Ensures each story is implementable (clear AC, API shape, non-goals)
  • Adds missing negative cases and boundary checks
  • Suggests subtasks (backend/ui/tests) where helpful
Output: upgraded Jira descriptions + readiness notes

Developer Agents (Backend / Frontend / Security)

  • Implement story requirements in small PRs
  • Prefer simplest working solution aligned with stack (Flask, JS)
  • Document decisions (API responses, error codes, assumptions)
Output: PR per story, "definition of done" checklist completed

Test Engineer Agent

  • Generate and maintain pytest + UI automation from AC
  • Understands fixtures, seeding, teardown to prevent flakiness
  • Keeps a traceability matrix (Story → tests)
Output: tests/ + stable test data strategy

CI Triage + Jira Update Agent

  • Monitors CI failures and categorizes them (bug vs flake vs env)
  • Posts actionable failure summaries back to the story
  • Transitions Jira statuses when PR is merged and CI is green

3) The sprint loop (Plan → Build → Test → Close → Next)

Step 0 — Readiness Gate (before sprint start)

  • Story has testable Acceptance Criteria
  • Dependencies satisfied (e.g., Auth before Transfers)
  • Definition of Done is known (tests required, docs required, etc.)
If not ready: Groomer agent updates ticket or the story is pushed out.

Step 1 — Sprint Planning (agent proposes, human approves)

  • Orchestrator selects candidate stories from Jira and drafts a sprint goal
  • Plan includes: scope, dependency order, risk notes, and “definition of done” reminders
Output: SPRINT_PLAN.md (reviewable artifact)

Step 2 — Execution (story-by-story PRs)

  • Developer agent implements a vertical slice (API + minimal UI if needed)
  • Test agent adds tests mapped to AC
  • CI runs; CI agent triages failures; iterate until green
  • Jira agent posts PR and CI links in the story
Definition of done: no story is “Done” unless CI is green and AC is met.

Step 3 — Sprint Review & Close

  • Generate sprint report: shipped items, known issues, carryover, tech debt
  • Transition completed stories; identify blocked items
  • Close sprint (if using Jira sprint feature) or publish a summary ticket/comment

Step 4 — Next sprint selection

  • Pick next stories based on backlog priority + next dependency chain
  • Include a small % capacity for stability (flake reduction, refactors, docs)

4) Guardrails (how to keep it safe and predictable)

Permission model

  • Wide read access (read backlog, comments)
  • Narrow write access initially:
    • comment
    • transition only forward
    • create subtasks (optional)

Engineering constraints

  • No direct pushes to main — PRs only
  • Require CI pass before “Done”
  • Prefer small PRs to reduce risk and review time

Truth hierarchy

If Jira says "Done" but CI is red → it’s NOT done. If CI is green but AC is missing → it’s NOT done. If AC is met and CI is green → ship it; then update Jira.

5) MVP rollout plan (start small)

The fastest path is to automate just enough to prove the loop works end-to-end. Then add sophistication (parallelization, auto-sprint close, richer reconciliation).

Phase 0 — Assisted mode (recommended)

  • Orchestrator writes a sprint plan from Jira
  • Developer agent implements 1 story and opens a PR
  • Human approves merge; Jira agent transitions the story

Phase 1 — Mostly automated

  • Auto-apply grooming template updates
  • Auto-generate tests from AC and keep CI green
  • Auto-transition Jira statuses based on PR/CI events

Phase 2 — Continuous backlog execution

  • Agent picks next best story when capacity frees up
  • Automated reconciliation keeps Jira + repo aligned
  • Periodic sprint summary generated and posted
