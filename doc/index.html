Purpose

Turn an SRS into a runnable backlog, tests, and CI — with AI agents

This guide reorganizes the ideas we discussed into a clean, reusable set of agent patterns. It’s designed for QA training projects (like SecureCore Bank), where consistency, traceability, and testability matter more than “magic automation”.

1) The automation contract (what “done” means)

Inputs

  • SRS The requirements document (e.g., SecureCore Bank.txt)
  • Jira Project (e.g., BAN) + issue types + workflow conventions
  • Templates Story template, Epic template, Definition of Done, naming rules

Outputs

  • Epics + stories/tasks with strong descriptions
  • Acceptance Criteria written to be testable
  • Linking stories grouped to epics + labels/components
  • QA Artifacts TEST_PLAN.md, BUG_REPORT_TEMPLATE.md
  • Automation pytest + Playwright/Selenium skeletons
Success criteria: If the SRS changes, you can re-run the pipeline to update Jira and docs without duplicating work or destroying manual edits.

2) Agent workflows that work well for Jira + QA projects

Think of agents as small specialists. Each one owns a narrow responsibility, produces a structured artifact, and hands off to the next.

Backlog Generator Agent High value

SRS → Epics/Stories with consistent templates

  • Extract epics, stories, and requirement IDs (FR/NFR/UI)
  • Write testable Acceptance Criteria (Given/When/Then)
  • Create issues in Jira and write a mapping file (Requirement → Jira key)
Output: backlog.yaml + jira-map.json

Backlog Reconciler Agent Drift control

Keeps Jira and your “source-of-truth” in sync

  • Fetch Jira issues created by the pipeline (labels/markers)
  • Diff vs backlog.yaml: detect missing/duplicate/changed tickets
  • Generate a reconciliation plan (create/update/link)
Output: reconcile-plan.md (human review) + optional apply

Acceptance Criteria Hardener Agent

Converts vague AC into test-ready contracts

  • Standardize API expectations: status codes, errors, “no state change” rules
  • Add negative cases and boundary conditions automatically
  • Include observability: audit log expectations, security headers
Output: updated Jira descriptions + AC checklist

Test Designer Agent

Acceptance Criteria → manual tests + automation skeletons

  • Generate manual test cases (TEST_PLAN.md) mapped to Jira keys
  • Create pytest stubs + fixtures + seed strategies (avoid flakiness)
  • Generate Playwright/Selenium test outlines using data-testid selectors
Output: tests/ + test data strategy + traceability matrix

Bug Triage Agent

Bug report → likely cause + reproduction + regression test idea

  • Summarize bug impact and suspected component
  • Propose minimal repro steps and expected behavior
  • Suggest a regression test to prevent recurrence
Output: triage notes + labels + suggested owner

Automation Maintainer Agent

Keeps the test suite green as the app evolves

  • Classify CI failures: product bug vs test flake vs environment
  • Propose stabilized selectors and deterministic waits
  • Improve fixtures and data isolation over time
Output: small PRs that reduce flakiness

Agile Assistant Agent (optional)

Backlog → sprint slicing, dependencies, risks, and demo plan

  • Suggest Sprint 1 scope based on dependencies (auth → accounts → transfers)
  • Call out risk hotspots (atomicity, concurrency, 2FA flow)
  • Create a “what to demo” list for end-of-sprint

3) Practical setup patterns (so it’s real and repeatable)

Make requirements machine-readable

  • Keep the SRS as the source document
  • Generate backlog.yaml as an intermediate artifact
  • Generate traceability.yaml for Requirement ↔ Jira ↔ Tests mapping
Repo folder idea: requirements/

Tag and isolate bot-created work

  • Add labels like generated-by-ai, securecore-bank, srs-v1.0
  • Store a Jira key mapping to avoid duplicates
  • Use consistent issue templates so updates are safe
Output: safer updates, easier filtering in Jira

Human-in-the-loop checkpoints (recommended)

A reliable pattern is: generate → review → apply. It avoids accidental Jira spam and keeps quality high.

Step 1: Agent generates backlog.yaml Step 2: Human reviews in PR Step 3: Agent applies changes to Jira

4) Common pitfalls & guardrails

Pitfall: duplicate tickets

  • Guardrail: use a requirement → Jira key map (stored in repo)
  • Guardrail: label bot-created issues, reconcile by label

Pitfall: untestable Acceptance Criteria

  • Guardrail: enforce a story template with explicit AC
  • Guardrail: add negative cases and boundary checks automatically

Pitfall: flaky UI automation

  • Guardrail: require data-testid selectors
  • Guardrail: deterministic test data and reliable waiting strategy

Pitfall: Jira field mismatch

  • Guardrail: keep an integration “capabilities check” step (discover fields)
  • Guardrail: fall back to bulk edit checklist when APIs don’t expose fields

Next steps you can do right away

Start small and win fast

  • Create a backlog.yaml generator from the SRS (even if first version is manual)
  • Build a “create/update Jira issues” step that reads backlog.yaml
  • Add an Acceptance Criteria hardener step that standardizes status codes + negative cases
  • Generate first-pass TEST_PLAN.md + test skeletons from Jira stories
