Deposit Flow

A deposit adds funds to the authenticated user's account. The amount is validated first; if it passes, the account balance is updated and a transaction record is inserted in the same commit.

sequenceDiagram actor Client participant API as POST /api/transactions/deposit participant JWT as JWT Middleware participant DB as Database Client->>API: Authorization: Bearer token + { amount } API->>JWT: Validate Bearer token JWT-->>API: user_id alt Token missing or invalid API-->>Client: 401 Unauthorized else Amount is less than $1.00 API-->>Client: 400 Minimum deposit is 1.00 else Amount exceeds $10,000.00 API-->>Client: 400 Maximum deposit is 10000.00 else Valid request API->>DB: SELECT accounts WHERE user_id = ? DB-->>API: account record API->>DB: UPDATE accounts SET balance = balance + amount API->>DB: INSERT transactions (type=deposit, amount) API->>DB: INSERT audit_logs (action=deposit, amount) API->>DB: COMMIT DB-->>API: OK API-->>Client: 201 { deposited, balance } end

Implementation Notes

  • The balance update and transaction insert happen in the same db.commit(). Any exception triggers db.rollback() in the except block.
  • Balance arithmetic uses Python's Decimal type to avoid floating-point rounding errors.
  • Related JIRA ticket: BAN-14.

Transfer Flow

A transfer moves money from the authenticated user (sender) to another registered user (recipient identified by email). Five validation checks run in sequence before any balance is modified. All DB writes occur in a single atomic commit (BAN-16).

sequenceDiagram actor Client participant API as POST /api/transactions/transfer participant JWT as JWT Middleware participant DB as Database Client->>API: Authorization: Bearer token + { to_email, amount } API->>JWT: Validate Bearer token JWT-->>API: user_id (sender) alt Token missing or invalid API-->>Client: 401 Unauthorized else Amount is less than $0.01 API-->>Client: 400 Minimum transfer is 0.01 else Recipient email not found API->>DB: INSERT audit_logs (transfer_failure, recipient_not_found) API->>DB: COMMIT API-->>Client: 400 Invalid recipient else Sender tries to transfer to self API->>DB: INSERT audit_logs (transfer_failure, self_transfer) API->>DB: COMMIT API-->>Client: 400 Cannot transfer to self else Insufficient funds API->>DB: INSERT audit_logs (transfer_failure, insufficient_funds) API->>DB: COMMIT API-->>Client: 400 Insufficient funds else Daily limit exceeded API->>DB: SELECT SUM(transfer_out) for today DB-->>API: daily_total API->>DB: INSERT audit_logs (transfer_failure, daily_limit) API->>DB: COMMIT API-->>Client: 400 Daily transfer limit exceeded else All checks pass API->>DB: SELECT SUM(transfer_out) for today DB-->>API: daily_total is within limit Note over API,DB: ATOMIC TRANSACTION (BAN-16) — single COMMIT API->>DB: UPDATE sender account.balance -= amount API->>DB: UPDATE recipient account.balance += amount API->>DB: INSERT transactions (type=transfer_out, sender_account) API->>DB: INSERT transactions (type=transfer_in, recipient_account) API->>DB: INSERT audit_logs (action=transfer, amount, to=email) API->>DB: COMMIT DB-->>API: OK API-->>Client: 201 { transferred, to } end

Atomicity Detail (BAN-16)

The transfer is the most critical operation for data integrity. The implementation ensures that either all of the following happen, or none do:

  1. Sender's balance decremented
  2. Recipient's balance incremented
  3. Two transaction ledger entries inserted (one transfer_out, one transfer_in)
  4. Audit log entry inserted

This is achieved with a single db.commit() at the end of the try-block. The outer except clause calls db.rollback() on any unexpected exception, preventing a partial state where one account is debited but the other is not credited.

✅
Atomicity guarantee: it is impossible for a transfer to reduce the sender's balance without equally increasing the recipient's balance, because both updates are in the same transaction.

Daily Limit Calculation

The daily transfer limit is computed dynamically per request:

SELECT COALESCE(SUM(amount), 0)
FROM transactions
WHERE account_id = sender_account.id
  AND type = 'transfer_out'
  AND DATE(created_at) = '<current UTC date>'

If daily_sum + requested_amount > $5,000.00, the request is rejected with HTTP 400.

Implementation Notes

  • Recipient lookup is case-insensitive (email is normalised to lowercase).
  • All five failure cases (recipient not found, self-transfer, insufficient funds, daily limit, minimum amount) produce an audit log entry before returning the error.
  • Related JIRA tickets: BAN-15 (transfer), BAN-16 (atomicity).
