Sprint Orchestrator (Mode 1)

Plan-only: read Jira → generate SPRINT_PLAN.md (no Jira writes)

← Overview GitHub Actions What it does Files Flow Tuning scope Safety
Outcome

Generate a sprint plan automatically from Jira, with a reviewable artifact

Mode 1 is intentionally conservative: it only reads from Jira and produces a sprint plan file. No transitions, no comments, no issue edits.

Input JQL + Jira secrets Output SPRINT_PLAN.md artifact Guarantee No Jira writes
Why this matters
This gives you a repeatable way to slice work into sprints using the same rules every time. You can review the plan before acting.

1) What Mode 1 does

Reads from Jira

  • Runs a JQL query (your backlog scope rules)
  • Fetches issue fields needed for planning
  • Normalizes into a clean JSON format
Output: tools/jira/issues.json

Generates a sprint plan

  • Builds a markdown table of candidate issues
  • Includes trimmed details per issue for quick review
  • Uploads the plan as a GitHub Actions artifact
Output: SPRINT_PLAN.md
Mode 1 constraint: no Jira writes. That’s why it’s safe as the first automation step.

2) Files added for Mode 1

Workflow

.github/workflows/sprint-orchestrator.yml
  • Manual trigger via workflow_dispatch with input maxResults
  • Optional schedule (weekly) for consistent planning cadence
  • Uploads artifacts: plan + issues.json + jql

Jira scripts

tools/jira/fetch_issues.py tools/jira/generate_sprint_plan.py tools/jira/jql.txt
  • fetch_issues.py: calls Jira REST API search endpoint with JQL and writes normalized JSON
  • generate_sprint_plan.py: reads normalized JSON and renders SPRINT_PLAN.md
  • jql.txt: your scope rules — edit this to control what enters the plan

3) End-to-end flow (what happens when you run it)

1) GitHub Actions starts 2) Workflow checks out the repo 3) Workflow sets up Python 3.11 4) fetch_issues.py runs: - reads tools/jira/jql.txt - calls Jira /rest/api/3/search - writes tools/jira/issues.json 5) generate_sprint_plan.py runs: - reads tools/jira/issues.json - writes SPRINT_PLAN.md 6) Workflow uploads artifacts for download
The plan is meant to be reviewed by a human before starting a sprint, moving statuses, or assigning work.

4) Tuning sprint scope (Option A)

Option A uses JQL based on status and rank. Your current default lives in tools/jira/jql.txt.

Default JQL

project = BAN AND issuetype in (Story, Bug, Task) AND status = "To Do" ORDER BY Rank ASC

Common tweaks

  • Add label gates: AND labels = ready-for-sprint
  • Exclude epics explicitly (already excluded by issue type list)
  • Limit to a component or sprint theme

About status naming

  • JQL status names must match your Jira workflow status names
  • “Backlog” in the UI is often a board bucket, not a real status

5) Safety / rollback model

Why this is safe

  • Read-only access to Jira
  • No state changes in Jira, ever (Mode 1)
  • Artifacts are reviewable and auditable

How we can evolve it later

  • Mode 2: add comments + optional transitions (guardrailed)
  • Mode 3: generate PRs per story
