CI / CD

GitHub Actions workflows for automated testing, sprint planning, Jira validation, and regression bug detection.

Workflow Overview

Workflow FileNameTriggerPurpose
api-regression.yml API Regression (pytest) Weekly (Mon 07:00 UTC) · Manual Runs the full pytest suite and uploads a JUnit XML test report as an artifact.
sprint-orchestrator.yml Sprint Orchestrator (Mode 1) Push to option-a/sprint-orchestrator · Weekly (Mon 08:00 UTC) · Manual Fetches Jira issues via JQL, generates SPRINT_PLAN.md, and uploads it as an artifact.
sprint-agent.yml Sprint Agent Manual Automates sprint-level Jira operations (labelling, status updates) for the active sprint.
regression-bug-agent.yml Regression Bug Agent Manual Runs tools/jira/regression_bug_agent.py to detect and file regression bugs from test failures.
verify-jira.yml Verify Jira Connection Manual Verifies that the Jira API credentials (secrets) are valid and the project is reachable.
verify-test-gate.yml Verify Test Gate Manual Validates that all sprint tickets linked to tests are passing before marking a sprint complete.

API Regression Workflow

File: .github/workflows/api-regression.yml

Runs the full test suite against a fresh SQLite database on every scheduled run or manual trigger. Uploads a JUnit XML results file as a downloadable artifact.

flowchart TD A([Trigger: Weekly Mon 07:00 UTC\nor workflow_dispatch]) --> B[Checkout repository] B --> C[Setup Python 3.11] C --> D[pip install -e . and dev extras] D --> E[pytest -q --junitxml=test-results/pytest-junit.xml] E --> F{Tests pass?} F -- Yes --> G[Upload test-results artifact] F -- No --> G G --> H([End])

Figure 7 — API Regression Workflow

Artifacts Produced

  • api-regression-results — contains test-results/pytest-junit.xml
  • The artifact is uploaded with if: always() so it is available even when tests fail.

Required Secrets

This workflow uses no secrets — it runs tests against a temporary in-memory SQLite database created by conftest.py.

Sprint Orchestrator Workflow

File: .github/workflows/sprint-orchestrator.yml

Connects to Jira, fetches candidate issues matching the configured JQL query, and generates a human-readable SPRINT_PLAN.md artifact. On push events, it only performs a syntax check (no live Jira calls).

flowchart TD T([Trigger: Push / Schedule / Manual]) --> A[Checkout repository] A --> B[Setup Python 3.11] B --> C{Event type?} C -- push --> D[Syntax check only\npy_compile + jql.txt exists] D --> END([End]) C -- schedule or dispatch --> E[Fetch issues from Jira\npython tools/jira/fetch_issues.py] E --> F[Generate SPRINT_PLAN.md\npython tools/jira/generate_sprint_plan.py] F --> G[Upload sprint-plan artifact\nSPRINT_PLAN.md + issues.json + jql.txt] G --> END

Figure 8 — Sprint Orchestrator Workflow

SecretDescription

Configuring the JQL Query

Edit tools/jira/jql.txt to change which issues are fetched. The default query selects all issues in the BAN project with label ready-for-sprint:

project = BAN AND labels = "ready-for-sprint" ORDER BY priority DESC

Artifacts Produced

  • sprint-plan — contains:
    • SPRINT_PLAN.md — generated Markdown sprint plan
    • tools/jira/issues.json — raw Jira issue data
    • tools/jira/jql.txt — the JQL query used

Running Jira Scripts Locally

Set your credentials in a .env file or as environment variables, then run any script directly:

# Set credentials
export JIRA_BASE_URL="https://yourorg.atlassian.net"
export JIRA_EMAIL="you@example.com"
export JIRA_API_TOKEN="your-api-token"

# Verify connection
python tools/jira/verify_connection.py

# Fetch issues
python tools/jira/fetch_issues.py \
  --jql-file tools/jira/jql.txt \
  --max-results 25 \
  --out tools/jira/issues.json

# Generate sprint plan
python tools/jira/generate_sprint_plan.py \
  --in tools/jira/issues.json \
  --out SPRINT_PLAN.md

Sprint Lifecycle (agile.py)

The tools/jira/agile.py module manages the full sprint lifecycle programmatically. The start_sprint() function was added to fix a gap where sprints were created and populated but never activated on the board.

⚠️
A sprint that is only created (state: future) is not visible on the active board and cannot be tracked. You must call start_sprint() to activate it.

Sprint State Machine

StateFunctionBoard VisibleTrackable
futurecreate_sprint()Backlog onlyNo
activestart_sprint()✅ Active board✅ Yes
closedclose_sprint()Reports onlyRead-only

Full Sprint Creation Workflow

from tools.jira.env import load_dotenv
load_dotenv()
from tools.jira.agile import create_sprint, add_issues_to_sprint, start_sprint

# 1. Create the sprint shell on board 34
sprint = create_sprint(34, "Sprint 3 - Frontend")
sprint_id = sprint["id"]          # e.g. 301

# 2. Move tickets from backlog into the sprint
add_issues_to_sprint(sprint_id, ["BAN-19", "BAN-20", "BAN-21", "BAN-22"])

# 3. Activate the sprint — this is what makes it visible on the board
start_sprint(
    sprint_id,
    start_date="2026-06-24T00:00:00.000Z",
    end_date="2026-07-07T00:00:00.000Z",
)

# 4. At end of sprint — close it
# close_sprint(sprint_id)
