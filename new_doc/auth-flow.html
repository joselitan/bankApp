Diagrams & Flows

Auth Flow

Sequence diagrams for user registration, login, and account lockout — including all error paths and audit log events.

Registration Flow

Registration creates a user and a default Savings account in a single atomic database transaction. If either operation fails, both are rolled back. An audit log entry is written regardless of outcome.

sequenceDiagram actor Client participant API as POST /api/auth/register participant DB as Database Client->>API: { email, full_name, password } API->>API: Validate password policy Note right of API: min 8 chars, 1 digit, 1 special char alt Password fails policy API->>DB: INSERT audit_logs (register_failure) API->>DB: COMMIT API-->>Client: 400 Bad Request else Email already registered API->>DB: INSERT audit_logs (register_failure, duplicate_email) API->>DB: COMMIT API-->>Client: 409 Conflict else Valid request API->>DB: BEGIN TRANSACTION API->>DB: INSERT users (email, full_name, password_hash) DB-->>API: user.id assigned API->>DB: INSERT accounts (Savings, balance=$0.00) DB-->>API: account_number generated API->>DB: INSERT audit_logs (register_success) API->>DB: COMMIT DB-->>API: OK API-->>Client: 201 { id, email, full_name, account_number } end

Figure 3 — Registration Sequence Diagram

Key Implementation Notes

  • The email is normalised to lowercase before storage and comparison.
  • The password is hashed with PBKDF2-SHA256 via passlib. The plaintext is never stored.
  • User creation and account creation are wrapped in a single db.begin() context manager — either both succeed or both are rolled back.
  • The account_number is a 16-character random hex string generated by secrets.token_hex(8). Uniqueness is enforced at the database layer.
  • Related JIRA tickets: BAN-6 (registration), BAN-10 (default account), BAN-18 (audit log).

Login Flow

Login validates the email and password, tracks failures, applies lockout, and returns a JWT token on success. The same generic error response is returned for both unknown email and wrong password to prevent user enumeration.

sequenceDiagram actor Client participant API as POST /api/auth/login participant DB as Database Client->>API: { email, password } API->>DB: SELECT users WHERE email = ? DB-->>API: user record or null alt User not found API->>DB: INSERT audit_logs (login_failure, unknown email) API->>DB: COMMIT API-->>Client: 401 Invalid credentials else Account is locked API->>DB: INSERT audit_logs (login_locked) API->>DB: COMMIT API-->>Client: 423 Account Locked else Wrong password API->>DB: UPDATE users SET failed_login_attempts++ Note right of API: if attempts >= 3 then set locked_until = now + 10 min API->>DB: INSERT audit_logs (login_failure) API->>DB: COMMIT API-->>Client: 401 Invalid credentials else Valid credentials API->>DB: UPDATE users SET failed_login_attempts=0, locked_until=null API->>DB: COMMIT API->>API: create_access_token(user.id) Note right of API: JWT HS256, expires in 30 minutes API-->>Client: 200 { access_token, token_type } end

Lockout Behavior Detail

The lockout is designed carefully to avoid revealing information:

Attempt #OutcomeResponse
1st bad passwordfailed_login_attempts = 1401 Invalid credentials
2nd bad passwordfailed_login_attempts = 2401 Invalid credentials
3rd bad passwordfailed_login_attempts = 3, locked_until = now+10min401 Invalid credentials
4th attempt (any)Lock detected before password check423 Account Locked
After 10 minutesLock expired, counter resets on next successNormal login flow resumes
ℹ️
The 3rd bad-password attempt still returns 401 Invalid credentials, not 423. The lock is activated for the next attempt. This prevents an attacker from knowing exactly when the account becomes locked.

JWT Token Overview

Tokens are HS256-signed JSON Web Tokens. The payload contains:

{
  "sub": "1",                  // user.id as a string
  "iat": 1749468000,           // issued-at (Unix timestamp)
  "exp": 1749469800            // expires-at (iat + 30 minutes)
}
PropertyValue
AlgorithmHS256
Expiry30 minutes from issue time
SecretSECRET_KEY env var (default: dev-only-change-me)
Subject (sub)Numeric user.id as a string
TransportAuthorization: Bearer <token> header
RevocationNot supported in MVP — short expiry is the only safeguard
⚠️
Always set a strong, random SECRET_KEY in any deployed environment. The default value is for local development only.
